# P0 技术决定记录（decisions）

- 基线：commit `29568a8a0a8aa9def7241d5d199bdf5d8a111adc`，分支 `codex/multi-user-auth`
- 生成时间：2026-10-05
- 依据：计划书第 2/3/4/5 节 + 源码静态盘点。每条标注状态：**已定**（计划书明确）/ **建议**（需项目负责人确认）/ **待 P2 定稿**。
- 本记录只做决定与依据，不做代码修改；P1 起按此执行。

## D1 目标数据库：PostgreSQL（建议，需确认）

- **决定**：以 PostgreSQL 18 为推荐业务主库，集中保存账号、权限、账本、业务查询、任务状态与审计（计划书表 1「业务数据库」）。
- **依据**：集中业务存储利于 C# 统一提交账户变化与任务状态；Python Worker 不直接写业务账本。
- **边界（计划书明确）**：
  - PostgreSQL 是"本计划新增建议"，现有系统尚未使用；引入会增加备份/维护/迁移工作，**须与语言替换分开提交**，不能混在一个大提交。
  - 事务隔离仍需配合行锁、唯一约束、冲突处理；仅换数据库不能避免并发更新错误。
  - 目标键必须含用户维度或显式映射；每个用户 DuckDB 的自增 ID 可能相同。
- **待 P2 定稿**：schema 版本化迁移工具、`operation_locks` 是迁 PG 表还是改用 PG 顾问锁、`daily_prices`/`instruments` 主档与 Python 分析侧（DuckDB/Parquet）的读写边界。
- **测试纪律（计划书 §8）**：集成测试用真实 PostgreSQL，测试库不用正式连接，不以 EF 内存提供器代替生产事务测试。

## D2 数值精度：decimal / numeric，禁止 double 中转

- **决定**：金额、费用、份额、成本用 **C# `decimal` + PostgreSQL `numeric`**；Python 侧沿用 `Decimal`。全程禁止经 `double` 再转回。
- **依据**：
  - C# `decimal` 有效精度约 28–29 位；Python `Decimal` 可能超此范围，**超范围记录须在导入前列出并决定映射，不能截断**。
  - 现有 Python 已用 Decimal，迁移**不宣称修复浮点问题**。
- **待 P0→P3 完成**：逐字段记录精度、取值范围、数据库 DECIMAL 定义、舍入时点、展示口径（计划书 §3「账本和数值」）。金额/份额响应保持十进制字符串；回测浮点指标误差在 P0 按旧基线定义，不在失败后放宽容差。

## D3 账号与密码兼容：Argon2id + 会话 + 跨语言验证向量

- **决定**：保留 Argon2id 密码哈希与 `quant_session` 不透明会话 + CSRF；用公开测试密码与测试哈希生成**跨语言验证向量**，核对参数、Unicode 输入、异常处理。
- **约束（计划书明确）**：
  - 选择经过维护并锁定版本的兼容实现；**禁止自行实现密码算法，禁止把 Argon2 哈希当 .NET 默认哈希**。
  - 保留账号 ID、用户名、角色、停用状态、管理员审计。
  - 正式切换撤销旧会话与旧恢复码，用户重新登录；原密码在兼容验证通过后继续可用。
  - 保留初始化、30 人硬上限、注册开关、停用、会话撤销、一次性恢复码语义，并验证并发注册。
  - 用户身份只来自已验证会话；内部接口必须认证并绑定任务/用户/当前尝试，不信任浏览器传的 `user_id`。保留 HTTPS、Origin、CSRF、限流、私有配置隔离与安全错误响应。

## D4 历史指纹：不得用 .NET 默认序列化重算覆盖

- **决定**：历史指纹 = Decimal 文本 + JSON 排序 + 时间表示，保留旧验证路径；不能用 .NET 默认序列化重新计算并覆盖旧指纹；必要时新增版本字段。
- **依据**：`ledger_replay_engine.py` / 快照校验依赖持久化 Parquet 行内容指纹与行数；`data/snapshots.py` 写入前统一行索引。
- **边界**：数值文本变化只能属于已证明等价且不影响旧指纹的映射；任何无法解释的差异阻止发布。

## D5 Worker 任务协议：DB 队列 + 内部 HTTP，幂等不保证恰好一次

- **决定**：统一任务契约核心字段：契约版本、`job_id`、`user_id`、输入快照 ID 与指纹、任务类型、`attempt`、`lease_token`、状态、截止时间、结果版本、安全错误码；契约变化版本化并带兼容测试。
- **机制（计划书 §5）**：
  - API 在数据库事务中创建任务；Worker 只领取已提交任务，通过**行锁 + 条件更新**获得租约，按当前尝试心跳续租；结果提交同时验证租约与尝试编号，旧 Worker 不能覆盖新状态。
  - 结果与终态原子保存，重复上报不重复影响业务。
  - **不承诺跨外部服务的恰好一次调用**（远端计费超时后无法判断）；含糊状态进入"待核对未知结果"，默认不自动重试。
- **范围**：首轮用数据库队列 + 内部 HTTP 接口；`operation_locks`/`job_heartbeats` 已存在，P4 映射到新协议。

## D6 回切方式：开放写入前可回退，写入后保护新库修复

- **决定**：
  1. 新系统**开放写入前**，可停止新服务回到被冻结的旧站点。
  2. 新系统**接受写入后**，旧快照已过期，直接回旧快照会丢新交易/账号变化；默认进入维护模式、保护新库并修复当前版本。
- **约束（计划书 §9）**：如需开放写入后仍能回旧站点，须在发布前提供覆盖全部新写入类型的**反向导出/导入演练**（账号、账本、审计、配置、文件、任务状态）；未完成反向演练时发布说明须明确该限制，不提供"恢复旧备份即可"的自动脚本。
- **部署边界**：开发阶段新旧站点不同端口/数据库/文件目录/测试凭据；切换前仅旧站可写正式数据，切换后仅新 API 可写。
