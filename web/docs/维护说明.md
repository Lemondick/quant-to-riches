# 网页版维护说明

当前运行版本采用 ASP.NET Core / C#、PostgreSQL 与受限 Python worker，前端为 Vue / TypeScript，使用原生启动器，不使用 Docker。部署、迁移、备份与恢复请以[原生维护手册](refactor/p7-runbook.md)为准。2026-10-07新增运行告警、跨年日历管理和 Windows 定时完整站点备份。

2026-10-08新增Windows服务适配器及安装器，常驻身份、证书、发布切换与回滚见[常驻运行手册](../backend-dotnet/deploy/native-service-runbook.md)。本轮仅在本机隔离环境验证，不安装正式服务、不切换正式数据、不安排24小时后台任务。实际验收与外部限制见[完整优化记录](refactor/native-all-optimization-20261008.md)。

配置`QUANT_LOG_DIR`后，API和宿主日志按日及20MB轮转，各最多30个文件。维护每分钟采样、每小时有界清理：最多1000份过期一天的未确认预览、1000份30天前可重复查询的公开行情任务；监控样本保留14天。已确认凭据、财务事实、付费任务和冻结报告来源保留。`QUANT_DISABLE_MAINTENANCE=true`可停用维护。

管理页显示最近5分钟最多4096次公开请求的P95、数据库活动/锁等待、最近两小时队列趋势和失败摘要。完整活动统计需要数据库角色具备`pg_read_all_stats`；权限不足时相关数值显示未知并提示，不能当作没有故障。数据库停机时`/healthz`和`/readyz`均返回503，数据库恢复、执行器心跳重新就绪后恢复200。

以下内容是冻结 Python / SQLite / DuckDB 旧版的维护参考；其中旧启动器、单用户备份、旧并发设置及 Docker 示例不适用于当前原生站点。

## 2026-10-05：多人站点完整备份与恢复

停止后端以及所有读写该数据目录的CLI任务后执行。完整备份持有站点锁，后端运行时会拒绝备份；同一数据目录只能运行一个后端进程。备份期间不要另行执行初始化、密码重置或数据导入。

```powershell
web/backend/.venv/Scripts/python.exe -B -X utf8 -m quant_assistant.site_backup create --data-dir data --output C:/Users/admin/Desktop/quant-site-backups/site-20261005.zip
```

包括账号库、所有用户数据库、偏好、自选、已保存报告、研究资料、年度日历和数据目录内其他业务事实。SQLite使用备份API，DuckDB检查文件锁并完成Checkpoint，默认排除运行目录、旧备份、`.key`、`.pem`、`.env*` 和 `server-secrets/`。原单账户备份不能替代完整备份。

密码哈希和金融数据属于私有备份；Windows输出权限限当前用户及SYSTEM，Linux文件权限600。需要迁移个人模型连接和Key时，另做显式 `--include-secrets` 的受控备份；目录外的 `deploy/` 私有配置需另行保管。压缩包没有加密，ACL只限制本机访问，迁移到其他介质后需自行保护。默认恢复后重新配置缺失的个人模型连接。

恢复目标必须不存在。验证清单、SHA-256、路径、SQLite完整性和DuckDB可读性后，才发布新目录，失败不覆盖现有数据。恢复撤销全部旧会话，用户重新登录：

```powershell

```

核对账号、持仓、现金、日期与模型连接，再用 ~~`web/backend/scripts/start_web.py --data-dir 新目录`~~ 启动（**作废**：`start_web.py` 拉起的是已退役的旧 Python 网页栈，当前生产为 C# 原生服务，见 `web/backend-dotnet/deploy/run-native.ps1` 与 `ubuntu-runbook.md`）。上述示例没有对本机真实数据执行备份或恢复。

## 2. 本机安装和启动

后端要求Python 3.11或3.12，前端需要Node.js/npm；依赖版本分别由`uv.lock`、`package-lock.json`冻结。

```powershell
uv sync --project web/backend --frozen --no-dev
npm --prefix web/frontend ci
.\启动网页版.ps1
```

默认地址：`http://127.0.0.1:8765/`。默认仅监听本机。
首次启动会构建网页；没有修改前端源码时可用：

```powershell
.\启动网页版.ps1 -SkipBuild
```

`-Port 8766`可以使用其他本机端口；同时修改浏览器连接地址。
重新构建会生成新的运行资源；重启前先核对有没有正在执行的AI任务，避免中断不确定的付费调用。
启动脚本发现已有相同服务时验证并复用，因此后端源码变更后应停止旧进程再启动。

要停止8765端口服务，先确定进程是本项目启动的后端，查看命令路径后再结束该PID：

```powershell
Get-NetTCPConnection -LocalPort 8765 -State Listen |
    Select-Object LocalAddress, LocalPort, OwningProcess
# 将下行的12345替换为已核实的项目后端PID
Get-CimInstance Win32_Process -Filter 'ProcessId=12345' |
    Select-Object ProcessId, ExecutablePath, CommandLine
Stop-Process -Id 12345
```

不要按“所有Python进程”批量结束，避免影响其他程序。

## 4. 模型与私有连接

首选网页设置中的连接和模型选择入口。输入自己的兼容API地址与Key，读取模型列表后选择资讯、策略、复核角色。
在同一设置页保存自己的Jev官方Key和决策模型；页面保存的模型角色属于用户配置，清理或升级不擅自改回默认模型。

管理者仍可读取原根目录`deploy/research-secrets/advisor.json`，可由`QUANT_ADVISOR_CONFIG`指定其他私有文件；普通用户不会继承此文件。
配置包含`enabled`、`endpoint`、`key_file`、`news_model`、`strategy_model`、`reviewer_model`、`jev_endpoint`、`jev_model`、`jev_key_file`等字段。
密钥文件路径由后端消费。更换文件前保留本机安全备份；不要把真实文件加入Git、源码ZIP、日志或截图。
报告创建时冻结角色选择，旧报告不随设置改变。

模型列表只证明接口返回的模型ID，不证明每个模型的所有功能都可用。
报告请求有日限额、证据约束和重复保护，不为了测试而无限重试付费调用。

## 5. 系统调度和交易日历

调度器位于`services/advisor_scheduler.py`，随API进程启动。
北京时间早间09:30–09:44、下午14:30–14:44，仅确认交易日执行。
任务、报告和系统内通知持久化；休市不生成提醒，错过窗口不补发。
本机需要保持开机和后端运行，聊天助手不承担生产调度。
交易日历源文件位于`services/advisor_scheduler.py`，当前覆盖2026年；扩展年份前根据正式休市安排核对。
worker 新增 `calendar.generate_next_year`（`web/worker/calendar_generation.py`）可按市场自动推算次年休市日：
US/JP/HK 为规则计算（confidence=high），CN 含农历与调休启发式（confidence=medium），
采用前必须与国务院办公厅当年 12 月公告核对，`notes` 字段注明了各项不确定性。

运维新增（2026-10-21）：10–12 月调度器每日检查次年日历，缺失时自动调 worker（`calendar.generate_next_year`）生成待确认版本并记 `admin_audit`，运维监控报 `calendar_auto_pending`；`QUANT_CALENDAR_AUTO_ACCEPT=true` 时交易日判定采纳未确认自动日历。定时报告失败后管理员可用 `POST /api/v1/admin/advisor/schedule/rerun` 手动重跑（窗口外需 `confirm=true`）。公开源连续 `QUANT_PUBLIC_SOURCE_FAIL_ALERT_ROUNDS`（默认 3）轮失败后给管理员写 `operational_alerts`（critical，`public_source:<provider>`），运维监控同步展示。模型日预算达 `QUANT_MODEL_BUDGET_WARN_RATIO`（默认 0.8）时费用汇总报 `budget_warn` 预警。

`scripts/run_market_advisor.py --scheduled`是维护入口，仍检查窗口和重复任务。
日常运行不额外安装Windows/Cron重复调度器，不使用`--force`绕过保护。

## 7. 备份与恢复

源码备份与账户备份是两件事。桌面的源码ZIP不含个人账户、密钥或环境。

完整本机备份步骤：

1. 确认没有正在执行的AI报告，停止本项目后端。
2. 将整个根目录`data/`复制到独立备份目录。
3. 将根目录私有`deploy/`单独复制到受控本机目录，不上传公开服务。
4. 记录备份时间与版本，再启动服务。

CLI也提供带校验的数据库备份：

```powershell
$env:QUANT_DATA_DIR = (Resolve-Path data).Path
web/backend/.venv/Scripts/python.exe -B -X utf8 -m quant_assistant.cli backup --output C:/Users/admin/Desktop/quant-account-backup.zip
```

此CLI ZIP包含数据库及存在的`config.toml`、`settings.json`，不等于备份所有偏好、新配置与模型Key。
完整迁移仍需上述完整目录备份。数据库由网页占用时先停止后端，避免文件锁冲突。

恢复先用一个新的空目录，检查校验结果及内容，不直接覆盖当前账户：

```powershell
web/backend/.venv/Scripts/python.exe -B -X utf8 -m quant_assistant.cli restore --input C:/Users/admin/Desktop/quant-account-backup.zip --target C:/Users/admin/Desktop/quant-restored-data
```

不要例行使用`--force`。恢复账户后重新核对日期、持仓、现金、净值、费率和批次。

### 月度自动恢复演练（2026-10-21 起）

`web/backend-dotnet/deploy/restore-drill.py` + `quant-restore-drill.service`/`quant-restore-drill.timer` 每月自动把最新归档恢复到**临时库 + 临时目录**做演练（生产库与站点目录不受影响），校验归档指纹与核心表数据，成功后在归档旁生成 `.restore.json`（管理页"备份恢复"证据显示恢复已验证）。失败时记日志、可配 webhook 告警（`QUANT_RESTORE_DRILL_ALERT_URL`），timer 单元显示 failed。安装与手动触发见 `web/backend-dotnet/deploy/ubuntu-runbook.md` §6。

## 12. 回算、运行与前向证据维护

历史成交补录只在当前用户账本执行。必须有唯一完整导入基线、原始事件审计及每个估值日所持资产的正式净值/收盘价快照。校验使用持久化Parquet行内容的指纹和行数，并核对账本价格与原始快照一致；新快照在写入前统一行索引。已有证据不重写，旧快照校验不一致时重新采集并保留原档案。校准与其他活动同日、补录与原事件同时发生且缺少先后证据、影响后续公司行动权益、转托管、待确认事件或原始审计缺失时停止重建，先核对完整权益数量及事件顺序。确认在事务中复查源指纹、文件内容和回算结果，保存修订前后持仓/净值及更新后的成本快照；失败回滚全部财务写入。

前向模拟计数现在由准入报告、模拟报告和观察脚本共同使用同一校验器。必须先冻结当时实际配置与实现指纹，然后在真实开市日收盘后实际生成决策并记录观察。仅版本名称相同不够；冻结后修改策略或风险参数、使用未知执行器、历史回算、过期来源、未终态模拟订单或缺最新成功对账均不能累计。无订单的当日也需要显式观察记录。`research_only`档案不可冻结或补造成准入证据。

> 风险等级：**高**。0035 把 `native_monitor_samples` 从普通表**重建**为按月 RANGE 分区表（全量回填 + 旧表删除），回滚要么重跑一次重建（`.down.sql`），要么从备份恢复。任何生产执行必须先过预检脚本（`web/backend-dotnet/deploy/preflight-partition.sh`，任一检查不满足就禁止执行）。

#### 13.3.1 风险与前提

- 0035 在 Runner 显式事务内执行：重建期间对旧表持有 `ACCESS EXCLUSIVE` 锁，任何写入者（API 的 `NativeRuntimeMaintenance` 每分钟写一行）必须在窗口内停止，否则要么迁移被锁阻塞、要么写入旧表的数据丢失（迁移期间写入旧表的数据不会自动进入新分区表）。
- 迁移内自带新旧表行数一致性校验：不一致则整事务回滚，表保持原样（这是安全的失败模式——但之后仍需排查再试）。
- 禁止给 0035 加 `-- quant:no-transaction` / `CREATE INDEX CONCURRENTLY`：PG 不支持在分区表上并发建索引（已实测报错），本迁移的索引是普通构建。
- 预计耗时参考：10 万行分钟级采样在本机 PG18 上重建+回填约数秒；生产以 staging 演练实测为准，**以实测时间的 3 倍**申报停机窗口。

#### 13.3.5 回滚预案

**路线 A（首选）：从备份恢复** —— 适用于"迁移已提交但数据不对"（如事后发现行数对不上、分区路由异常）。

```bash

  -p EnvironmentFile=/etc/quant/environment \
```

### 13.5 分区表维护注意事项

- 不要对该表做大范围 `DELETE`（整分区 DROP 由定时器处理，又快又不膨胀）；临时排查用只读查询。
- 新写查询尽量带 `captured_at` 范围条件以利用分区裁剪；`ORDER BY captured_at DESC LIMIT n` 走覆盖索引，无需回表。
- 监控 `native_monitor_samples_default` 分区行数：正常应为 0，有行进入说明出现时钟偏移或异常时间戳写入，需排查。
- 手工建分区必须用命名规范 `native_monitor_samples_pYYYYMM`，否则清理函数会跳过（防误删）；`DEFAULT` 分区永不自动删除。
- 不要修改分区键、不要在分区表上加不含分区键的唯一约束（PG 分区表要求唯一约束包含分区键）。
- `pg_dump` 正常备份分区表；恢复后分区结构保留。
- 已知冲突：`NativeRuntimeMaintenance.Clean()` 目前每小时删除 14 天前的采样行，与 90 天保留策略冲突——在 A 流将其阈值改为 `QUANT_SNAPSHOT_RETENTION_TICK_DAYS` 之前，分区里超过 14 天的数据仍会被应用层删掉（待 A 流跟进）。

## 14. 2FA（TOTP）运维管理（2026-10-21 起，任务11，A 流实现）

以下按 batch2 契约编写，具体以后端实现为准：TOTP 密钥存 `users` 表新列（迁移 0033，A 流），恢复码经 bcrypt 哈希后存 `user_totp_recovery` 表；登录流程为密码通过 → 若启用 2FA 则要求 TOTP 码 → 通过才发 session；验证器 App 显示的发行人为 `QUANT_TOTP_ISSUER`（默认“观澜”）。

- 密钥列只在登录验证路径读取：管理员后台永不展示明文密钥，只能做“重置 2FA”（重置操作记入 `admin_audit` 哈希链）。
- 用户丢失验证器/恢复码：管理员在用户详情页签发新恢复码（一次性、15 分钟有效，参考现有密码恢复码流程），用户用恢复码登录后重新绑定；恢复码是 bcrypt 哈希，不可逆，遗失只能重新签发。
- 用户主动关闭 2FA：在设置页用当前 TOTP 码二次确认后关闭；管理员强制关闭同样记审计。
- 服务器时间必须 NTP 同步：TOTP 按 30 秒步进，时钟漂移过大会导致全员验证码失效，表现为登录页大面积 2FA 失败而密码正常。
- 备份恢复后 2FA 密钥随 `users` 表一起恢复，无需额外操作；切勿把密钥列导出到公开渠道。

## 15. 审计链验证（2026-10-21 起，任务12）

`admin_audit` 通过 `prev_hash`/`hash` 列构成哈希链（口径见[功能说明](功能说明.md) §22 与 `0036_audit_hash_chain.sql` 文件头，A 流写入端逐字遵守）。

手工验证（直连数据库，不依赖应用进程）：

```bash
# 默认：0036 之前的历史遗留行（hash IS NULL）仅警告跳过
web/backend-dotnet/deploy/verify-audit-chain.sh
# 严格模式：遗留行也视为失败（要求全表入链后使用）
web/backend-dotnet/deploy/verify-audit-chain.sh --strict
```

连接：`QUANT_PG_CONNECTION`（Npgsql 风格）或 `PGHOST/PGPORT/PGUSER/PGDATABASE/PGPASSWORD`。退出码：0=链完整；1=断裂或哈希不匹配；2=用法/连接/查询错误。脚本逐条重算 `SHA256(prev_hash||actor_id||action||target_id||detail||created_at_utc)` 并检查相邻行 `prev_hash == 上一条 hash`；`preimage` 拼接在 SQL 侧完成以保证字节精确。

链断裂应急：

1. 立即停止管理员写入（停后端 API），防止断裂扩大；
2. 按脚本输出的 `id` 定位断裂/篡改行，在数据库核对该行及相邻行的 `prev_hash`/`hash`；
3. 若为误操作或单行损坏：从 F2 备份恢复 `admin_audit` 到断裂前状态，或接受断裂点并书面记录原因（链断裂后新行仍可续链，但断裂点永久可查，`--strict` 会持续报警）；
4. 查清原因（重点排查是否有绕过 `AdminAuditRepository` 的直写 SQL）后再恢复服务；
5. 管理员后台另有“验证审计链”按钮（`GET api/v1/admin/audit/verify`，A 流实现），与本脚本口径一致，可交叉核对。

注意：回滚 0036（`.down.sql`）会永久删除已计算的链数据，回滚前请先备份 `admin_audit`。

## 16. 慢查询告警、任务优先级与限流配置（2026-10-21 起，批量三期）

配置键走 `QuantOptions`（Options 模式），改配置后重启后端 API 生效。

### 16.1 慢查询告警阈值

- `QUANT_SLOW_QUERY_ALERT_P95_MS`（默认 2000）：单条 SQL 的 P95 耗时超过该
  毫秒数即计为慢查询。
- `QUANT_SLOW_QUERY_ALERT_MIN_COUNT`（默认 20，单位：次/小时）：一小时内慢
  查询达到该次数触发告警。

两个条件同时满足才告警，避免偶发抖动打扰。收到告警后先看慢查询明细定位
SQL，再决定加索引还是改写法；不要直接调高阈值掩盖问题。

### 16.2 任务优先级与 starvation 防护

任务优先级常量：`critical` > `high` > `normal`。调度按优先级出队；
starvation 防护：`normal` 任务等待超过 `QUANT_TASK_QUEUE_MAX_LOW_WAIT_MIN`
（默认 120 分钟）自动提级一次，防止低优任务长期饿死。

运维注意：提级只发生一次；若 normal 任务持续积压，说明 worker 容量不足，
应扩容或排查卡死的 high/critical 任务，而不是继续放宽等待阈值。

### 16.3 限流配置

- `QUANT_RATE_LIMIT_PER_MIN`（默认 100）：普通 API 每用户每分钟请求上限。
- `QUANT_RATE_LIMIT_LOGIN_PER_MIN`：登录接口保持现有更严策略，**不动**。

限流为后端内存滑动窗口实现（Redis-less），计数不持久化（见迁移
`0041_rate_limit_placeholder` 的占位说明）；多实例部署时各实例独立计数，
未来如需集中持久化计数，另起迁移编号实现。

### 16.4 模型去重缓存

- `QUANT_MODEL_CACHE_ENABLED`（默认 true）：总开关。
- `QUANT_MODEL_CACHE_TTL_MIN`（默认 60）：缓存有效期（分钟）。

缓存表 `model_call_cache`（迁移 0040）：键为
`sha256(model_version + canonical_json(prompt))`；命中返回 `cached: true`
并 `hits` +1。过期行由清理任务删除；关闭总开关后新请求不再读写缓存，
已存行保留至过期。

### 16.5 CSP 上报（report-only）运维

生产 Caddyfile 以 `Content-Security-Policy-Report-Only` 模式下发 CSP
（只观察、不阻断），违规上报到 `POST /api/v1/csp-report`（流 A 后端实现，
只收不存 PII，记 metrics）。上报量突增通常意味着前端引用了新外部资源，
先在报告里确认来源合法，再决定收紧或放宽策略。

如需从观察模式切换为强制模式：把生产 Caddyfile 的
`Content-Security-Policy-Report-Only` 改为 `Content-Security-Policy` 并重载。
**警告**：切换前必须先跑至少一周 report-only 且报告干净，否则可能直接打断
页面脚本/样式；CI 的 `security-headers` job 会阻断强制版头部的误提交
（只允许 Report-Only 落库），切换时需同步更新该检查。

## 17. 日志保留策略与磁盘水位告警（2026-10-21 起，batch4 任务 #7）

Serilog 文件日志（API：`api-*.jsonl`，NativeService：`host-*.log`）保持原有
策略不变：按天滚动（`rollingInterval: Day`）+ 单文件 20MB 上限（`rollOnFileSizeLimit`），
在此基础上保留期改为可配置：

| 配置键 | 默认 | 说明 |

| `QUANT_LOG_RETENTION_DAYS` | 30 | 日志保留天数；`retainedFileCountLimit` 与之对齐。API 走 `QuantOptions`；NativeService（Windows）从服务配置 JSON 的 `Environment` 中读取同名键，非法值回退 30（钳制 1..3650）。改小会删旧日志，改大注意磁盘。 |

磁盘水位告警（`NativeOperationsMonitor` 站点级告警，管理页"运维状态"可见）：

- `QUANT_DISK_ALERT_THRESHOLD_PCT`（默认 80，钳制 1..99）：任一监控盘（站点存储/备份存储/**日志存储**）使用率超过该阈值即发出 `disk_usage_high` **warning** 告警，提示检查归档和日志保留。
- 早于原有的 `QUANT_DISK_MIN_FREE_PERCENT`（默认 10，可用空间不足 → `disk_low` **critical**）水位，是前置预警。
- 监控输出 `disks[]` 新增 `used_percent` / `usage_alert_percent` 字段供前端展示。
