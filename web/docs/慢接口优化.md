# 慢接口优化（batch5 #7）

## 数据来源与方法

- batch3 的 `SlowRequestAggregator` 是**纯内存实现**（进程重启清零、只保留近 2 小时桶、每桶上限 10000 样本），
  本工作区没有生产样本可输出 Top5（p95/调用量）。按任务约定，改用**代码审查**确定候选，
  依据：用户高频页面 × 单次请求 DB round-trip 次数 × 是否存在可避免的排序/全表扫描。
- before/after 计量：本地 PG18 + 合成数据（`attribution_reports` 5 万行/20 用户、
  `transactions` 5 万行/20 用户、`goal_targets` 2 万行/20 用户、
  `portfolio_valuations` 2000 行、`fund_announcements` 6 万行），
  `EXPLAIN (ANALYZE, TIMING OFF)` 取 Execution Time。
  注意这是 DB 执行耗时，不含应用↔DB 网络往返；round-trip 减少的收益在异机部署的生产环境更大。
- 播种脚本与 benchmark SQL 保留在验证机 `/tmp/batch5-perf/`（临时文件，不入库）。

## Top5 清单与结论

| # | 接口 | 瓶颈 | 优化 | before | after |
|---|---|---|---|---|---|
| 1 | `GET /api/v1/attribution/reports`（归因报告列表） | 分页 `ORDER BY created_at DESC, id DESC` 无匹配索引：5 万行过滤 + 全量排序 | 新增 `attribution_reports_user_created(user_id, created_at DESC, id DESC)`（0049 迁移） | 3.44 ms（Bitmap/Seq + Sort） | **0.26 ms**（Index Scan + LIMIT 提前止，约 13×） |
| 2 | `GET /api/v1/net-worth?history_days=`（净值历史曲线） | `portfolio_valuations` 仅有 `(user_id)` 索引，日期范围 + 排序走 filter + sort | 新增 `portfolio_valuations_user_asof(user_id, as_of_date)`（0049 迁移） | 0.52 ms | **0.13 ms**（约 4×） |
| 3 | `POST /api/v1/goals/{id}/project`（目标投影） | 先 SELECT 目标行、再 UPDATE `current_amount`：除账本查询外 2 次 round-trip | 合并为单条 `UPDATE … RETURNING`（`GoalTargetRepository.RefreshAndGetAsync`，batch5-#7） | 3 次 DB round-trip | **2 次**（worker 计算耗时占主导，DB 侧省 1 次往返） |
| 4 | `GET /api/v1/history/onboarding`（新手引导状态） | 4 次独立 `count(*)`（positions/cash/valuations/reports） | 合并为单条 `SELECT` 标量子查询（`HistoryRepository.Onboarding`，batch5-#7） | 4 次 round-trip | **1 次**（0.45 ms） |
| 5 | `GET /api/v1/goals`（目标列表） | `ORDER BY target_date` 无复合索引 | 新增 `goal_targets_user_target_date(user_id, target_date)`（0048 迁移） | 1.15 ms | 1.18 ms（该数据分布下 planner 仍选 bitmap + sort；索引为目标数多时的上限保护，属防御性优化） |

## 评估后未采用的优化（负向结论，同样记录）

- **count(*) + 分页合并为 `COUNT(*) OVER()`**（曾在公告列表、归因列表、账本历史三处试过）：
  窗口函数迫使匹配行全量物化后再做 top-N，实测反而更慢——公告 9.36 ms vs 两次独立查询 7.2 ms；
  账本历史 45.9 ms vs 27.3 ms——**已全部回退**，保留原两次独立查询（均已走索引）。
- **账本历史 `transactions` 覆盖索引** `(user_id, traded_at DESC, id DESC) INCLUDE (…)`：
  `UNION ALL` 形态下 planner 仍选 seq scan，未采用。

## 遗留与说明

- 生产 p95 口径仍以 `SlowRequestAggregator`（`/api/v1/admin/ops` 的 `slow_requests`）与
  `operational_alerts` 的 `slow_query` 告警为准；本结论基于合成数据，生产验证待线上观察。
- 单机自托管场景下每用户数据量小（数千行），多数接口 DB 耗时已在 5 ms 内；
  真正的慢风险在 worker 计算类 op（如 `goal.project` 的任务排队等待），不在 DB 层。
- 新增索引随 0048/0049 迁移一并上线（幂等 `IF NOT EXISTS`）；回滚见各自 `.down.sql`。
