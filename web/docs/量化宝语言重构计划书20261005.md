# 量化宝语言重构计划书

> 2026-10-06 执行修订：用户已授权 Codex 直接完成迁移及测试修复，取消 GML 交接和分阶段 review。部署改为原生 Windows / Linux + PostgreSQL 18 + Caddy，不使用 Docker。以下初版阶段划分作为历史计划保留；当前交付以 [实施状态](refactor/native-migration-progress.md) 和 [原生运行手册](refactor/p7-runbook.md) 为准。


版本 1.0　日期 2026年10月5日　执行 GML　代码审查 Codex　发布决定 项目负责人

本计划供 GML 实施、Codex 分阶段 review。目标是让量化宝在单台服务器上长期服务自己或几十名用户，减少维护中的类型错误，并让账本、后台任务和数据恢复具有可验证的运行边界。推荐采用 C# 与 ASP.NET Core 10 作为业务主后端、Vue 3 与 TypeScript 作为前端、Python 作为数据采集和量化研究 Worker。

实施方式为逐模块开发和独立环境验证，最后在维护窗口统一切换正式站点。现有 Python 站点在切换前继续承担正式写入；迁移开发不触碰真实账户、密钥、账本和证据目录。第一份交付只执行 P0，提交审查后再推进后续阶段。

## 1 实施依据和目标

### 1.1 当前代码基线

本计划依据仓库提交 `29568a8a0a8aa9def7241d5d199bdf5d8a111adc`，分支 `codex/multi-user-auth`。编写计划前工作区无未提交改动。GML 开始执行时必须重新记录 HEAD、分支和工作区状态；发生变化时先更新清单，不能直接沿用本计划中的数量。

当前前端是 JavaScript、Vue 3 和 Uni-App H5，后端是 Python、FastAPI 和 Uvicorn。账号库使用 SQLite，业务数据按用户保存到 DuckDB，管理员沿用根数据目录，普通用户使用独立子目录。主体为 MVC 加业务服务层的模块化单体，包含后台线程、定时报告、子进程研究和可选容器 Worker。

当前源代码目录有 227 个 Python 文件、56 个 Vue 文件和20个 JavaScript 文件；主 `schema.sql` 有54条建表语句。这不是完整数据库清单，服务中的动态建表、SQLite表、JSON配置和原始文件也必须在 P0 盘点。

`web/docs/STATUS.md` 报告已有后端63项离线验收及四组前端组件验收。它还说明浏览器视觉验收、Docker实际运行和真实外部模型调用未全部覆盖。本次编写计划没有重新运行这些测试，GML 必须在隔离环境复跑并提交结果。

### 1.2 需要达到的结果

- 现有功能和接口继续可用，用户可以登录、核对持仓、导入账本、查询历史、查看研究与报告。
- 已确认现金、份额、费用、成本和事件顺序保持一致，未知数据继续保持未知。
- 单用户的重复提交、同账户并发写入和故障重启不会形成重复入账或部分提交。
- 外部行情、OCR、模型和研究任务的故障不会阻塞普通账户查询。
- 完整站点备份可以在空环境恢复；发布失败有明确的数据处理和回切方式。
- GML 每阶段交付可运行代码、测试证据和迁移说明，Codex 可以独立复现和审查。

## 2 目标技术方案

### 2.1 技术选择

| 部分 | 目标方案 | 迁移边界 |
| --- | --- | --- |
| 业务后端 | C# 与 ASP.NET Core 10 LTS | 账号、权限、账本、业务查询、任务状态和API |
| 前端 | Vue 3 与 TypeScript | 保留页面和Uni-App H5，逐步替换JavaScript |
| 研究计算 | Python 3.11或3.12 | 保留采集、Pandas、NumPy、因子、回测和模型适配 |
| 业务数据库 | PostgreSQL 18 | 本计划新增建议，集中保存业务事实和持久化任务 |
| 分析存储 | DuckDB与原始文件 | 供Python分析使用，由对应进程单独拥有 |
| 部署 | 单台服务器与Docker Compose及Caddy | 前端静态资源、API、数据库、Worker和持久化卷 |

.NET 10 官方支持到2028年11月14日；生产使用受支持的维护补丁，具体镜像和包版本在 P0 锁定。PostgreSQL 是本计划提出的目标数据库，现有系统尚未使用它。引入它会增加备份、维护和数据迁移工作，因此需在 P0 提交技术决定和恢复演练方案，不能与语言替换混在一个大提交中。[官方 .NET 支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)

集中业务存储有利于 C# 统一提交账户变化和任务状态。Python Worker 通过内部任务接口读取输入并提交结果，不直接修改业务账本。PostgreSQL 的事务隔离仍需配合行锁、唯一约束和冲突处理；仅仅换数据库不能避免并发更新错误。[PostgreSQL 事务隔离文档](https://www.postgresql.org/docs/current/transaction-iso.html)

### 2.2 运行和代码结构

正式站点的请求方向为：浏览器 → Caddy → ASP.NET Core API → 业务服务 → PostgreSQL。后台工作方向为：API事务保存任务 → Python Worker领取 → 计算或外部调用 → 内部接口提交结果 → C#校验并保存。

建议新增 `web/backend-dotnet/`，包含 `QuantAssistant.Api`、`QuantAssistant.Core`、`QuantAssistant.Infrastructure` 和 `tests/`。API负责HTTP及认证，Core包含业务规则和接口，Infrastructure包含PostgreSQL、文件和Worker适配。先采用这三个项目，按功能组织代码；不引入额外的总线、通用仓储框架或多层包装。

`web/backend/` 在过渡期保留完整旧站点。Worker宿主和任务适配可以新增在 `web/worker/`，复用已有Python包；避免复制两套因子或回测实现。`web/frontend/` 保留当前视图，`web/deploy/` 增加新部署配置，`web/docs/refactor/` 保存接口清单、决定、验收报告和审查记录。

整个站点仍采用模块化单体业务后端。独立 Worker 用于隔离计算和外部请求。首轮不引入 Kubernetes、Redis、RabbitMQ、微服务拆分、UI重设计和真实交易执行。

### 2.3 正式写入边界

开发阶段新旧站点使用不同端口、数据库、文件目录和测试凭据。新站点的账本写入只发生在测试环境；不能用正式请求同时写新旧数据库来验证结果。

切换前只有旧站点可以写正式业务数据。切换后只有新API可以写正式业务数据库，Python Worker不能写旧账本。旧数据作为受保护的备份保留。数据核对使用冻结快照和同一组输入，不能把时间不同的两份实时结果当作一致性证据。

## 3 必须保留的业务行为

### 3.1 接口与前端兼容

P0 必须生成包含HTTP方法、路径、请求字段、响应字段、状态码、错误码、分页、超时和权限要求的完整清单。主业务OpenAPI、认证和管理员接口、运行管理接口都要覆盖；不能只导出一个用户业务应用的OpenAPI。

保留 `/api/v1` 接口、字段名、数字与字符串形式、null语义及用户可理解的错误消息。现有封闭模型拒绝额外字段及非有限数值；C#必须保持这些行为。ASP.NET Core默认的400校验错误、ProblemDetails响应、枚举解析和数字序列化不能直接取代旧422响应或旧错误结构。需要改变契约时另开版本并更新前端及验收用例。

先从 `models/api.js`、`models/auth.js`、公共控制器和工具函数引入TypeScript，再迁移页面。保留页面地址、交互、图表、账号切换清缓存和防旧请求覆盖新状态的逻辑。开启strict，例外逐项记录；不以全局any或关闭检查完成迁移。[TypeScript 迁移文档](https://www.typescriptlang.org/docs/handbook/migrating-from-javascript.html)

### 3.2 账本和数值

现有Python已经使用Decimal，迁移不能宣称是在修复所有浮点问题。先逐字段记录精度、取值范围、数据库DECIMAL定义、舍入时点和展示口径。金额、费用、份额、成本使用C# decimal和PostgreSQL numeric，禁止经过double再转回。C# decimal有效精度约28至29位，Python Decimal可能超出此范围；超范围记录必须在导入前列出并决定映射，不能截断。[C# 数值类型文档](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/floating-point-numeric-types)

现金、持仓、交易、分红、公司行动、批次、校准、冲正和审计必须按旧规则组成事务。批量提交任一项失败时整体回滚。同账户并发变化需要数据库锁或并发版本，不能只依赖API进程内的锁。重复提交按用户、操作类型和幂等编号识别；同编号不同内容返回冲突。

保留基金和股票同代码的资产类型区分、T+1、基金批次、费率证据时效、卖出前成本、关联事件校验、预览有效期、源指纹及确认条件。补录和冲正继续保留历史证据，不用覆盖历史记录代替业务冲正。

### 3.3 账号与安全

当前密码是Argon2id哈希，登录使用 `quant_session` 不透明会话和CSRF。用公开测试密码与测试哈希生成跨语言验证向量，核对参数、Unicode输入和异常处理。选择经过维护并锁定版本的兼容实现，禁止自行实现密码算法或把Argon2哈希当成.NET默认哈希。

迁移保留账号ID、用户名、角色、停用状态和管理员审计。正式切换撤销旧会话与旧恢复码，用户重新登录；原密码在兼容验证通过后继续可用。初始化、30人总上限、注册开关、停用、会话撤销及一次性恢复保持原语义，并验证并发注册。

用户身份只来自已验证会话。所有查询、关联键、缓存、导出、预览和任务都要按用户隔离；管理员敏感读取继续记录审计。内部接口必须认证并绑定任务、用户和当前执行尝试，不能信任浏览器传来的user_id或普通请求头。保留HTTPS、Origin与CSRF校验、限流、私有配置隔离和安全错误响应。

### 3.4 时间与历史证据

业务日期和交易日历保持Asia/Shanghai语义，存储时区转换必须显式。保留同一时间点的旧事件排序规则。历史指纹包含Decimal文本、JSON排序和时间表示，不能用.NET默认序列化重新计算并覆盖旧指纹；必要时新增版本字段，并保留旧验证路径。

本次重构不修改策略收益、研究窗口、模拟天数或交易准入标准。缺证据、缺成本、缺模型用量或价格继续保持未知或阻止操作；历史重放、测试日历和72小时运行测试都不计为真实前向交易日。重构通过不等于研究准入通过。

## 4 数据迁移方案

### 4.1 建立完整映射

清单必须覆盖SQLite账号与审计表、每个用户的DuckDB、服务动态创建的表、偏好、自选、模型配置、照片导入状态、研究快照、报告、年度日历、原始证据和文件引用。每个来源都要注明迁移到PostgreSQL、保留文件、保留Python分析库或明确不迁移的原因。

原先每个用户数据库中的自增ID可能相同。目标键必须包含用户维度或使用显式映射，相关外键一起转换。原账号ID和可公开引用的业务ID尽量保持；确需更换时保存旧新映射。数据库序列在导入后校准，验证第一笔新写入不会与历史ID冲突。

私有密钥不得进入清单、日志、测试仓库或提交。迁移时通过受限文件或配置引用保持可用，单独验证权限。旧文件路径要经根目录校验并转为明确的存储引用，不能让用户输入决定任意文件路径。

### 4.2 导出和导入步骤

1. 在隔离数据副本运行盘点和dry-run，不连接正式数据库或付费模型。
2. 正式演练先停止写入和调度，等待任务结束；存在无法确认的调用时记录未知状态，避免自动再次付费。
3. 使用已有完整站点备份流程生成冻结源，校验文件清单及SHA-256；仅复制正在写入的数据库文件不算有效备份。
4. 导出带schema版本、用户映射、数量、数值范围和文件引用的中间数据。保留Decimal原文本、时间和旧指纹，不经浮点转换。
5. 导入空的目标数据库和独立文件根目录，记录迁移批次；重复导入不会增加重复业务事实，失败目标不发布。
6. 对每个用户核对现金、份额、成本、费用、交易数量、事件顺序、批次余额、报告及证据引用。归一化表结构时提供可解释的数量映射。
7. 运行账号、业务、任务、导出和备份恢复验收；生成机器可读差异和审查报告。

准确的账本字段要求差异为零；数值文本变化只能属于已证明等价且不影响旧指纹的映射。回测浮点指标允许的误差必须在 P0 按旧基线定义，不能在失败后放宽容差。迁移报告中任何缺失、重复或无法解释的差异都阻止发布。

### 4.3 新备份格式

为新站点设计有版本号的完整备份，包含PostgreSQL一致性导出、所有用户相关文件、日历、必要配置引用和校验清单。数据库与文件快照需要同一冻结边界，恢复到空目录和空数据库后验证引用及内容，再启用服务。

旧备份必须继续能恢复旧站点；新恢复器若不直接支持旧格式，应提供明确的旧恢复加新导入路径。恢复时撤销会话和恢复码，模型任务进入可核对状态，不能自动重复执行历史付费调用。数据库备份与秘密恢复流程分开，不在普通下载包里暴露私有密钥。

## 5 后台任务和故障隔离

### 5.1 持久化任务协议

先记录现有研究、报告、模型调用和调度状态，再制定统一任务契约。核心字段包括契约版本、job_id、user_id、输入快照ID与指纹、任务类型、attempt、lease_token、状态、截止时间、结果版本和安全错误码。契约变化需版本化并具有兼容测试。

新API在数据库事务中创建任务。Worker只领取已提交任务，通过行锁与条件更新获得租约，按当前尝试心跳续租；结果提交同时验证租约和尝试编号，旧Worker不能覆盖新状态。结果和终态保存要原子完成，重复上报不会重复影响业务。首轮使用数据库队列与内部HTTP接口即可。

“重启后不重复入账”可通过事务和幂等约束实现。远端模型是否已计费在超时后可能无法判断，因此不能承诺跨外部服务的恰好一次调用。含糊状态进入需核对的未知结果，默认不自动重试；已知未发送的失败、幂等公开查询按规则有限重试。

### 5.2 生命周期与运行管理

轻量调度和任务协调可使用.NET BackgroundService；计算、采集和模型调用由独立Python进程承担。后台生命周期仍必须有持久化记录，服务退出时停止领取、取消可取消任务、等待排空并保存最终可核对状态。[ASP.NET Core 后台服务文档](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0)

保留全站模型并发默认3、按用户授权、重复任务限制和成本口径。金额预算在无法证明调用前token上限时继续阻止付费调用。不能为了完成重构而取消当前预算保护、来源校验或研究输出校验。

外部适配必须定义连接与读取超时、重试条件、并发上限、缓存期限和取消行为。日志关联request_id、job_id和attempt，但不记录密码、Cookie、Key、私有模型配置或完整账户正文。任务积压、失败、耗时和Worker心跳需要能够查询。

### P0 固定基线

GML 盘点所有入口、路由、数据库、动态表、配置和文件，生成模块迁移矩阵。复跑现有离线验收，建立合成及脱敏测试样本，保存旧接口响应和账本结果。提交关于PostgreSQL、数值精度、账号兼容、历史指纹、Worker协议和回切方式的决定记录。

交付 `baseline.md`、`api-inventory.json`、`storage-map.md`、验收样本及测试报告。报告注明测试目录、依赖版本、命令、结果和未验证范围。此阶段不改产品代码、不启动真实外部调用、不搬动正式数据。Codex 核对清单覆盖和规则口径后进入 P1。

### P1 建立后端骨架

新增 .NET 10 controller-based Web API、Core和Infrastructure项目，开启nullable和编译警告检查，锁定依赖。建立异常转换、请求ID、配置校验、认证管线、健康接口和OpenAPI，保持旧响应契约。增加dotnet build、dotnet test及现有前后端检查的CI步骤。

交付可在测试环境启动的骨架、架构说明和接口契约测试。数据库、Worker和私有配置不可用时给出安全且可判定的状态。骨架验收只覆盖已实现能力，未实现接口不得返回伪造成功。

### P2 实现存储迁移与账号

建立PostgreSQL schema、用户隔离、约束和迁移版本。实现冻结数据导出、重复导入保护、差异报告及空环境恢复。实现登录、注册、权限、会话撤销、恢复码、管理者初始化和账号审计，验证Argon2id兼容。

交付完整存储映射、迁移工具、认证及跨用户访问测试。至少两份独立演练目标的核对结果一致。30人上限及并发注册、停用和敏感读取审计通过。测试使用临时账号，正式凭据不进入报告。

### P3 迁移账本与持仓

迁移账户快照、现金、持仓、成交、分红、资金流、公司行动、批次、校准、冲正、补录和对账。首先固定事务与数值规则，再逐接口实现。采用同一冻结样本分别驱动旧Python服务和新C#服务，逐事件比较账本结果。

交付业务迁移代码、差异报告及事务故障测试。覆盖部分提交、相同代码不同资产、同账户并发卖出、重复确认、过期预览、旧成本缺失和关联事件。任一账本差异未解释即阻止进入正式切换；不能通过改样本期望值消除差异。

### P4 接入后台任务和Python

实现任务协议、领取租约、续租、取消、结果幂等及重启恢复。保留Python研究计算和数据适配，迁移其对业务库的直接写入为内部结果提交。通过Mock模型覆盖超时、Worker强制退出、数据库中断、旧租约回报和未知计费状态。

交付Worker宿主、任务契约、运行指标和故障报告。AI或采集故障时账户查询仍可用，全站模型并发和预算规则有效。旧研究角色、输入限制、快照验证和准入边界保持，测试不调用付费模型。

### P5 完成功能与前端类型迁移

迁移基金资料、估值、费用、研究、报告、历史分页导出、照片导入、管理员详情、使用统计和运行维护接口。Python负责适合复用的采集与解析，C#负责授权、业务变更和保存。逐项关闭接口清单中的缺口，不以转发旧业务站点作为最终迁移完成条件。

逐步把前端公共模型、控制器、工具及页面迁移到TypeScript，保持现有页面。交付完整接口覆盖报告、类型检查、组件测试和浏览器真实流程证据。生成TS类型时还要保留运行时校验，静态类型不能验证外部接口实际返回值。

### P6 验证部署和恢复

在与目标服务器相同的拓扑启动Compose，验证Caddy转发、HTTPS、持久化卷、权限和重启。进行备份恢复、磁盘满、数据库不可达、Worker崩溃、模型超时及部署中断测试，并执行30用户负载与72小时持续运行。

交付固定镜像和锁文件、部署手册、备份恢复脚本、性能及运行报告、发布和回切演练。生产镜像不依赖开发源码挂载，容器重建不丢数据。未覆盖真实模型或OCR时明确列出，不能把Mock成功写成真实外部链路通过。

### P7 受控切换正式站点

在review完成后准备发布包和最终数据清单，由项目负责人决定维护窗口。按第9节执行冻结、备份、最终导入、只读核对、开放写入和观察。GML提交切换后的核对报告，Codex review发布差异和运行结果。

交付正式版本号、迁移批次、完整恢复点、功能核对及遗留问题清单。保留旧版本镜像和旧数据，暂不清理归档。生产开放写入后出现问题，按最新数据边界处理，不能直接恢复旧快照覆盖已确认的新交易。

## 7 验收标准

### 7.1 业务与兼容

现有验收全部复跑，新旧接口清单没有未说明的缺口；每个迁移模块有对应测试。HTTP契约比较只忽略P0列明的动态字段，不能忽略金额、用户ID、事件序列或业务状态。正常、无权限、无效输入和业务冲突都要比较。

完整用户流程覆盖登录、停用与恢复、账号切换、截图预览和确认、持仓、费用与批次、冲正和补录、历史分页及导出、模型设置、报告状态、管理者审计和完整站点恢复。研究准入、证据时效和未知值边界与旧实现一致。

### 7.2 故障与数据

| 场景 | 验收结果 |
| --- | --- |
| 批量入账中途失败 | 整个业务事务回滚且审计可核对 |
| 同请求重复或并发提交 | 只形成一次业务效果或明确冲突 |
| 同账户并发卖出 | 不出现超卖或丢失更新 |
| API和Worker强制重启 | 已提交账本不丢失任务状态可核对 |
| 模型发送后响应未知 | 不盲目再次付费状态保持待核对 |
| 旧Worker迟到提交结果 | 不能覆盖当前尝试和结果 |
| 数据库不可用或磁盘满 | 写入失败可判定readyz降级无部分提交 |
| 备份文件损坏或缺引用 | 恢复拒绝发布目标且不覆盖现有数据 |
| 跨账号ID和缓存访问 | 访问被拒绝且无其他用户数据泄露 |

### 7.3 运行目标

以下是建议验收门槛，不是当前实测能力。P0记录参考硬件，暂按4核CPU、8GB内存、SSD及30个用户测量；实际服务器不同则在测试前修订指标。

- 在30用户、总计10请求每秒的持续查询负载下，本地或缓存读取API的p95不超过800毫秒，p99不超过2秒；模型、OCR及回测结果计算不计入此延迟指标。
- 持续30分钟的正常负载中，预期有效请求没有无法解释的5xx，业务正确性和用户隔离不受影响。
- 三个Mock研究任务运行期间，普通读取继续满足延迟目标；外部故障得到独立状态，服务存活不依赖外部接口立即成功。
- 72小时持续运行覆盖固定查询、账本样本、调度和重启，进程无未解释退出，任务无永久挂起，内存没有持续增长趋势，报告记录峰值和稳定区间。
- 数据库或必要业务配置不可用时 `/readyz` 返回不可用；Worker失效和任务积压通过明确状态暴露，不能由容器存活代替业务健康。
- 在明确参考数据量上，备份恢复目标为30分钟内，维护切换目标为30分钟内；演练超时必须先优化或更新窗口，不在正式切换现场猜测耗时。

进程故障时已确认入账事务不能丢失。整机或磁盘故障的数据恢复能力取决于异机备份频率；单台服务器不承诺硬件故障下零数据丢失。建议每日完整备份并验证异机副本，先以24小时灾难恢复点目标执行，所需存储位置在 P0 记录。

## 9 发布和回切

1. 固定已review的版本、镜像、数据库schema和恢复包；重新核对任务、用户和文件清单。
2. 进入维护模式，停止新的写入及自动任务，等待已执行任务排空；保存不能确认的外部调用状态。
3. 取得完整冻结备份，校验来源和完整性，最终导入新库；旧库与旧文件保持受保护状态。
4. 核对每个用户和关键业务，任一差异阻止下一步；失败时旧站点仍是有效数据来源。
5. 切换Caddy到新API，撤销旧会话，暂保持只读；核对登录、读取、导出和任务状态。
6. review及项目负责人确认发布结果后开放写入，记录新系统第一笔写入边界，逐项恢复调度。
7. 核对首批真实使用结果，持续观察24至72小时，保留最终导入日志、恢复点和运行报告。

新系统开放写入前，可以停止新服务并回到被冻结的旧站点。新系统接受写入后，旧快照已经过期；直接回旧快照会丢失新交易或账号变化。此时默认进入维护模式、保护新库并修复当前版本。

如业务要求开放写入后仍能回到旧站点，GML必须在发布前提供覆盖全部新写入类型的反向导出和导入演练，包含账号、账本、审计、配置、文件和任务状态；转换后逐项核对最新业务事实，之后才能启动旧服务。未完成反向演练时，发布说明明确这一限制，不能提供“恢复旧备份即可”的自动脚本。
