# 数据库迁移规范

> 归属：C 流（E19）。与《跨流契约》§2 配套；契约变更优先。

## 1. 编号段（严格，不许越界）

| 流 | 编号段 | 内容 |
|---|---|---|
| A | 0025、0026 | 0025 只读角色；0026 用户业务写操作统一审计表 |
| B | （无） | B 不得新建迁移 |
| C | 0027、0028、0029 | 0027 触发器优化；0028 `site_settings` 加 `calendar_policy` 键；0029 备用（仅 C 必要时） |
| D | 0030 | `fx_rates` 汇率表 |

文件命名：`NNNN_<name>.sql`（如 `0027_trigger_optimization.sql`），与同目录可选的回滚文件 `NNNN_<name>.down.sql` 同名对应。

## 2. 老迁移 grandfather 规则

`0001`–`0024` **原样保留、不许修改**。它们不可重入（依赖 `schema_migrations` 版本表去重）；需要修正其行为时，一律用新编号迁移做 `DROP ... IF EXISTS` + 重建（如 0027 对 0020/0021/0024 的做法），不得回头改旧文件。

## 3. 新迁移必须幂等（E19）

`0027` 起的所有新迁移必须可重入，允许的写法：

- `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`
- `CREATE INDEX IF NOT EXISTS`
- `INSERT ... ON CONFLICT (key) DO NOTHING`（`site_settings` 等键值表）
- `CREATE OR REPLACE FUNCTION`
- `DROP TRIGGER IF EXISTS ... ON <表>` + `CREATE TRIGGER`（`CREATE TRIGGER` 本身无 `IF NOT EXISTS`，必须先 DROP）
- `DROP FUNCTION IF EXISTS`

禁止在新迁移里写不可重入的裸 `CREATE TABLE` / 裸 `INSERT` / 裸 `CREATE TRIGGER`。

## 4. 回滚约定（E2，A 实现 Runner）

- 每个迁移可配可选的同名 `.down.sql`（如 `0027_trigger_optimization.down.sql`）。
- 缺 down 文件时，Runner 的 `--rollback-to <version>` 直接拒绝并提示，不做猜测性回滚。
- down 文件同样遵守幂等写法。

## 5. `--dry-run` 与 `--no-transaction`（A 在 E2 里实现，C 只用文件侧机制）

- `--dry-run`：Runner 试运行全部待应用迁移、不提交、不写 `schema_migrations`。CI 的 `migration-dry-run` job（C/E21）在每次提交时调用该接口做迁移冒烟测试。
- `--no-transaction`：给未来 `CREATE INDEX CONCURRENTLY` 等**不能在事务块内执行**的语句用（PostgreSQL 限制；Runner 默认单事务执行迁移，见 E19 分析）。
  - 约定：含此类语句的迁移必须在文件头注释第一行注明 `需要 --no-transaction`，并在提交说明里写清原因；
  - C 不修改 `MigrationRunner.cs`（归 A），只在迁移文件侧遵守该标记的用法。

## 6. 触发器编写约定（0027 起）

- `AFTER` 触发器必须带 `WHEN` 子句做窄过滤（如只监听终态流转），避免每次 UPDATE 都逐行执行函数体；notify 语义（queued/completed/released）不得丢失。
- CPU 密集型校验（如 fund.catalog 逐元素正则）**不得放在行级触发器里**：触发器内只做廉价的结构 + 数量上限检查，逐元素校验约定由 worker/应用层在落库前完成（0027 迁移头注释记录了该假设与过渡期语义）。
- 需要按行聚合的计数器（如 `users.data_revision`）优先用语句级触发器 + `REFERENCING OLD/NEW TABLE` 批量合并，避免批量导入时的逐行锁争用。
